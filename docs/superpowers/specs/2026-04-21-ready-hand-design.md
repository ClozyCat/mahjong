# 麻将“听牌”功能设计方案

**日期**：2026-04-21  
**状态**：已完成设计确认，待用户审阅  
**范围**：为当前麻将项目新增“听”宣告、听牌状态、自动出牌、听牌成和计番与对应前端呈现

## 1. 背景与目标

当前项目已经具备以下基础能力：

- 前端可根据本家手牌推导当前听牌信息，以及“打出某张牌后会听什么”。
- 后端已具备完整的出牌、吃碰杠和、超时自动动作、结算与番数计算链路。
- 牌桌舞台已经支持“吃 / 碰 / 杠 / 和”这类楷体动作提示。

但系统目前缺少正式的“听牌”规则能力，导致以下需求无法满足：

- 玩家无法在“打出所选牌即可听牌”时主动宣告“听”。
- 服务端无法记录玩家已听牌，因此无法可靠约束后续操作。
- 听牌后的“摸到非自摸牌自动打出”无法由规则层统一处理。
- 通过听牌和了时，系统无法增加“听牌成和”这一番。

本次设计目标如下：

- 在本地人类玩家主动宣告的范围内新增“听”功能。
- 后端状态设计保持通用，为未来 AI 或其他座位支持主动听牌预留空间。
- 听牌后的锁手、自动出牌、和牌判断、计番全部由后端裁决，前端只负责投影与交互呈现。
- 保持现有对局节奏，不引入额外确认步骤，不改变非听牌玩家的既有行为。

## 2. 已确认的范围边界

本次设计已确认以下约束：

- 只支持本地玩家主动点击“听”按钮。
- 后端状态与规则实现必须保持通用，不写死“只对本地玩家有效”。
- “听牌成和”只要玩家在和牌前已经成功宣告过听，就一律成立。
- “听牌成和”不区分 `自摸` 与 `点炮`，均计 2 番。
- UI 细节必须满足：
  - “听”按钮显示在“出牌”按钮右侧。
  - “听”按钮使用主题色描边风格。
  - 玩家宣告“听”时，桌面上显示楷体字“听”，风格与现有“吃 / 碰 / 杠 / 和”统一。

## 3. 方案对比与结论

### 3.1 推荐方案：后端正式听牌状态 + 前端投影

做法：

- 后端新增正式动作 `ready_hand`。
- 后端在玩家回合状态中记录是否已听牌。
- 前端根据后端投影决定何时显示“听”按钮与何时锁手。
- 后端负责听牌后的自动出牌与加番。

优点：

- 规则闭环完整，前后端不会因本地计算差异而状态不一致。
- 锁手、自动出牌、加番都能统一走现有规则引擎与结算链路。
- 后续若要扩展到 AI 或其他座位，不需要重构协议语义。

缺点：

- 需要同时改动前端动作投影、后端状态机、自动动作与计番。

### 3.2 备选方案：前端主导的本地听牌标记

做法：

- 前端自己判断能否听牌并显示“听”按钮。
- 点击后仍向后端发送普通 `discard`，本地再附加“已听”状态。

问题：

- 服务端不知道谁已经听牌，无法可靠限制后续操作。
- 听牌后的自动打牌无法稳定实现。
- 计番时无法以服务端权威状态判断“听牌成和”。

该方案不采用。

### 3.3 备选方案：复用 `discard`，在参数中塞入“听牌意图”

做法：

- 不新增动作类型，而是在出牌请求上附加“本次是听牌出牌”的附加语义。

问题：

- 动作语义不清晰，校验与事件表达会变得模糊。
- 不利于未来维护和测试。
- 仍然需要额外状态落点，本质复杂度并未减少。

该方案不采用。

### 3.4 最终结论

本次采用“后端正式听牌状态 + 前端投影”的方案，动作命名使用 `ready_hand`，不直接使用拼音命名。

## 4. 领域模型与状态设计

### 4.1 新增动作类型

后端动作体系新增：

- `ready_hand`

语义定义：

- 该动作表示“玩家宣告听牌，并同步打出本次所选的那张牌”。
- 它不是“先进入听牌状态，再等待单独出牌”的两步流程，而是一次原子动作。

前端相关类型同步新增：

- `BackendActionType`
- `PromptActionType`
- `ActionRequestType`
- `BattleActionId`

### 4.2 玩家回合状态

`PlayerRoundState` 新增通用字段：

- `is_ready_hand: bool`

语义定义：

- `false`：本局尚未宣告听牌。
- `true`：本局已宣告听牌，直到本局结算前保持为真。

该状态不因座位类型不同而改变解释方式，因此未来 AI 或远端玩家也可复用。

### 4.3 投影与快照

前端快照需要能够感知本家是否已听牌，至少需要投影出：

- 本家是否处于听牌状态。
- 当前主动回合是否允许 `ready_hand`。

推荐做法：

- 在 `private_state.players[*]` 的投影中透出 `is_ready_hand`。
- 在主动回合的 `pending_action.options` 中，按规则加入 `ready_hand`。

这样前端按钮显示逻辑只依赖已有的投影体系，不额外发明旁路字段。

## 5. 行为规则设计

### 5.1 “听”按钮的出现条件

“听”按钮只在以下条件同时满足时显示：

- 当前是本地玩家自己的主动回合。
- 当前本来允许出牌。
- 本地玩家当前只选中 1 张手牌。
- 该牌当前可合法打出，不能是受限弃牌，也不能是花牌。
- 以前端现有的听牌推导逻辑计算，打出该牌后 waits 数量大于 0。
- 本家尚未处于听牌状态。

按钮位置与样式要求：

- 放在“出牌”按钮右侧。
- 使用主题色描边样式，不使用“和牌”那种高强调火焰风格。

### 5.2 `ready_hand` 动作校验

后端接收 `ready_hand` 时必须校验：

- 当前处于 `playing` 阶段。
- 当前 `pending_action` 为本玩家的主动回合。
- 行为发起者是当前行动玩家。
- 请求中仅带 1 张待打出的 `tile_id`。
- 该牌属于当前玩家的暗手牌。
- 该牌当前允许被打出。
- 将该牌从暗手牌中移除后，玩家的牌型确实进入听牌状态。

若任一条件不满足，则拒绝动作并返回现有错误通道。

### 5.3 宣告后的状态变化

`ready_hand` 成功后立即发生以下状态变化：

- 将选中的牌按正常出牌流程打出。
- 对应玩家 `is_ready_hand = true`。
- 推进弃牌后的后续流程，包括被其他玩家吃碰杠和的响应窗口。
- 发出新的 `round_event`，用于前端显示“听”字动作提示。

推荐增加专用事件：

- `ready_hand_declared`

事件最少应包含：

- `seat`
- `discard_tile_id`
- `discard_tile_key`

同一次 `ready_hand` 必须同时产生：

- 普通 `tile_discarded` 事件，用于维持牌河、claim window 与后续回合推进逻辑。
- `ready_hand_declared` 事件，用于前端显示“听”字动作提示。

事件顺序要求：

- 先发 `tile_discarded`
- 后发 `ready_hand_declared`

这样既能保留现有弃牌语义，又能让前端把“听”视为最新动作特效。

## 6. 听牌后的回合与自动动作

### 6.1 锁手规则

玩家处于听牌状态后，不再允许手动操作自己的暗手牌。

具体表现：

- 前端手牌按钮全部禁用。
- 前端不再允许点选、双击出牌、切换吃碰杠组合。
- 后端对该玩家的主动回合不再向前端投影可手动点击的普通 `discard` 交互；若当前不可 `hu`，则直接进入自动出牌链路。

注意：

- 听牌状态并不剥夺和牌权。
- 若当前规则允许该玩家在满足条件时和牌，则仍然保留 `hu` 响应。

### 6.2 摸牌后的自动处理规则

听牌玩家进入自己的主动回合并摸牌后，按以下顺序处理：

1. 若摸到花牌，先按现有补花流程处理。
2. 补花完成后若再次摸牌，继续应用本规则。
3. 若当前可自摸，则保留 `hu`，不自动打牌。
4. 若当前不可自摸，则系统立即自动打出本次摸到的那张牌。

自动打出的目标牌定义为：

- 本次主动回合最新摸到的那张牌。
- 不重新开放自由选牌，也不对听牌玩家做新的弃牌决策。

### 6.3 自动动作实现方式

本项目已有两类自动化能力：

- bot 自动操作
- timeout 到期自动操作

本次设计不采用“等待 30 秒后再帮听牌玩家出牌”的方式，而是新增或扩展统一自动化入口，使其同时支持：

- bot 玩家自动行动
- 听牌玩家的强制自动行动

推荐实现方向：

- 在 `automation` / `scheduler` 中扩展“自动行动者”概念，而不是仅限 bot。
- 当轮到听牌玩家主动回合且当前不可 `hu` 时，立即调度自动出牌。

广播顺序要求：

- 前端仍应先感知到摸牌，再发生自动打牌。
- 若现有消息链路无法天然保证这一点，实现阶段必须显式检查并调整事件顺序。

## 7. 前端交互与呈现设计

### 7.1 手牌区

非听牌状态下：

- 保持现有点选、双击出牌逻辑。

听牌状态下：

- 本地手牌全部禁用。
- 仍可显示当前听牌信息弹层，但不允许通过点牌改变操作结果。

### 7.2 Ready hand 信息弹层

当前项目已有 ready-hand insight 弹层，本次不删除，继续复用：

- 未听牌时：用于提示“当前听什么”或“打出所选牌后听什么”。
- 已听牌时：仍可作为纯信息展示，帮助玩家知道自己在等哪些牌。

### 7.3 底部动作按钮

动作区新增“听”按钮：

- 文案为“听”。
- 顺序位于“出牌”右侧。
- 使用主题色描边样式。

动作优先级要求：

- 不覆盖“和牌”的高优先级。
- 与“出牌”同层展示，体现“这是主动回合中的另一种合法操作”。

### 7.4 牌桌动作提示

新增桌面 callout：

- 文案为楷体字“听”。
- 触发来源为 `ready_hand_declared` 事件。
- 动效与现有“吃 / 碰 / 杠 / 和”统一，但配色可使用主题色系，避免和“和牌”混淆。

## 8. 计番与结算设计

### 8.1 新增番种

新增番种：

- `ready_hand_win`

显示文案：

- `听牌成和`

番值：

- `2`

### 8.2 成立条件

若赢家在本局和牌前已经成功宣告过听，则该番成立。

不区分：

- `self_draw`
- `discard`

只要赢家 `is_ready_hand == true` 且本次为和牌结算，即可加此番。

### 8.3 结算入口

推荐在后端结算输入中显式传入“赢家是否听牌”的上下文，然后在 scoring evaluator 中增加 fan rule。

这样可以保持：

- 规则判断明确
- fan key 稳定
- 前端结果面板只做 fan key 到中文文案的映射

前端需要同步补齐：

- `fanGuide` 中的中文名称与说明
- 结果面板中的番数展示

## 10. 错误处理与兼容性要求

### 10.1 非法听牌请求

以下情况必须拒绝：

- 非当前行动玩家发起 `ready_hand`
- 选择了 0 张或多张牌
- 选择的牌不在暗手牌中
- 该牌当前不允许打出
- 打出后并未进入听牌
- 玩家已经处于听牌状态却再次宣告听

拒绝时：

- 不得改变房间状态
- 不得改变暗手牌
- 不得污染弃牌河

### 10.2 兼容性原则

新增功能不得改变以下既有行为：

- 非听牌玩家的普通摸打流程
- 吃碰杠和的已有优先级与 claim window 行为
- 结算结构和既有 fan key 的语义
- bot 的既有决策逻辑

## 11. 测试与验证策略

### 11.1 后端测试

至少覆盖以下场景：

- 合法 `ready_hand` 动作可成功，并设置 `is_ready_hand`
- 非法 `ready_hand` 被拒绝，状态不变
- 听牌后摸到不可自摸的普通牌，系统自动打出该摸牌
- 听牌后摸到可自摸牌，不自动打出，并保留 `hu`
- 听牌后若先补花再摸牌，仍继续走自动处理链
- 听牌成和时 fan breakdown 包含 `ready_hand_win`
- `ready_hand_win` 固定计 2 番，且自摸、点炮都生效

### 11.2 前端测试

至少覆盖以下场景：

- 满足条件时显示“听”按钮
- “听”按钮顺序位于“出牌”右侧
- “听”按钮使用主题描边样式类
- 已听牌后本地手牌禁用
- 收到 `ready_hand_declared` 事件后，桌面显示楷体“听” callout
- 结果面板显示“听牌成和”

### 11.3 完成前验证

实现阶段完成后，至少进行：

- 前端相关单元测试
- 后端相关单元测试
- 一次联调式冒烟验证，确认“宣告听 -> 自动打牌 / 可和牌 -> 结算加番”完整闭环成立

## 12. 风险与控制

主要风险：

- 自动打牌链路与现有 timeout / bot 自动化发生职责重叠。
- 事件顺序若处理不当，前端可能看不到摸牌再自动弃牌的连续反馈。
- 若前端只做按钮显示、未正确锁手，可能出现“显示已听但还能手选出牌”的假状态。

控制策略：

- 以后端状态为唯一权威，前端不自行维护听牌真假。
- 优先复用现有 discard / claim / settlement 链路，只把“听”作为其前置标记和自动化入口。
- 对自动动作与结算新增定向测试，避免只测 UI 按钮不测规则闭环。

## 13. 最终设计结论

本方案将“听”定义为一次原子动作 `ready_hand`：玩家点击后立即打出所选牌，并进入本局持续生效的听牌状态。

进入听牌状态后：

- 玩家不能再手动操作自己的牌。
- 后续摸到花牌继续补花。
- 后续摸到可自摸牌时保留和牌机会。
- 后续摸到不可自摸牌时自动打出该摸牌。

若玩家最终和牌，则额外增加 `ready_hand_win` 这一番，前端显示为“听牌成和”，计 2 番。

后续实现应以此文档为设计基线，按照“后端规则闭环优先、前端只做投影与交互呈现”的原则推进。
